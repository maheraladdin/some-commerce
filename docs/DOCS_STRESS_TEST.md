# Documentation stress test and gap register

Review date: **2026-11-03**. Scope: README, four system guides, all **51** story specifications, module catalogs, **12** sprint plans, and documentation scripts. Method: compare requirements and dependencies, walk adversarial and failure scenarios, inspect design examples, and verify selected protocol/platform constraints against primary sources. This is a specification review, not a runtime load test, penetration test, or completed compliance audit.

## Result

The specifications describe the happy paths well enough to start design discussions, but they do **not** establish production readiness. The largest gaps are tenant/privacy boundaries, financial state transitions, synchronization correctness, and evidence for claimed guarantees. The [quality gates](QUALITY_GATES.md) and each story's validation section are now normative acceptance requirements. Unresolved items below block the affected story at G0 or G4 as specified. No application verification has occurred.

**Priority:** P0 blocks implementing the affected design until the contract is resolved; P1 blocks marking the affected story Done/releasing it; P2 is documentation/process debt. Owners below are accountable roles; assign named people in each story's evidence record. Deadlines are dependency milestones, not an assumed delivery date. “Open” means the gate is specified but the design decision and evidence are still required.

## Verified constraints behind the findings

- DynamoDB GSIs provide eventual reads. Therefore a wall-clock high-watermark alone does not prove all earlier writes have been observed; F02 requires a completeness protocol. [AWS read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html).
- Redis Pub/Sub delivers at most once and loses messages when a subscriber cannot receive them. F03 is an architectural inference: invalidation needs a bounded recovery mechanism. [Redis delivery semantics](https://redis.io/docs/latest/develop/pubsub/).
- `If-Match` uses strong entity-tag comparison; weak tags do not match it. F04 requires distinct write preconditions and atomic persistence checks. [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match).
- DynamoDB transactions are limited to 100 distinct items and 4 MB, within one account/Region. F11 cannot promise an unbounded atomic rewrite. [AWS transaction constraints](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).
- Rust 2024 became available in Rust 1.85. Dynamic trait dispatch also has constraints on generic methods; the port examples need a deliberate static-vs-dynamic design. [Rust edition guide](https://doc.rust-lang.org/edition-guide/rust-2024/index.html), [Rust trait reference](https://doc.rust-lang.org/reference/items/traits.html#dyn-compatibility).
- Cognito documents distinct OTP, WebAuthn, custom, and OAuth-related flows. The stories must select and validate the actual supported integration rather than combine labels from different flows. [Cognito authentication flows](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-authentication-flow-methods.html).

These checks do not certify other version, cost, legal, tax, Marketplace, carrier, cryptographic service, or region-availability claims in the original guides. Those remain inputs to the affected story's G0/G2 review.

## Closing a finding

Link the chosen decision/ADR, updated conflicting requirements, implementation PR, failing-then-passing regression test or independent audit evidence, reviewer, and source commit. Update status only after the required evidence exists. A new checklist, a diagram, or a green documentation lint run does not close a runtime/design finding. Repeat the affected story gates when the contract changes.
